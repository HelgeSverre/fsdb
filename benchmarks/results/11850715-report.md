# Performance report for `11850715`

This report summarizes the complete standard latency suite and the
durability-matched write suite. The raw measurements are in
[`11850715.md`](11850715.md) and
[`11850715-durable.md`](11850715-durable.md).

## Scope and interpretation

The standard run measured every registered SQL workload on fsdb and MySQL,
plus the separate connection benchmark. It covers 127 paired workloads: core
reads and writes, authentication and catalogs, views, CTEs, subqueries, joins,
windows, JSON, full-text search, spatial lookup, secondary and functional
indexes, ordering and grouping, and compressed wire traffic.

Each latency result used three warmup iterations and six measured iterations
on an Apple M2 Max with .NET 10.0.11 and MySQL 8.4.11. The standard dataset has
10,000 users, 50,000 orders, and 10,000 articles.

The standard comparison is in-memory fsdb against durable MySQL. It is useful
for reads and feature-to-feature comparisons, but it gives fsdb an artificial
durability advantage on writes. The separate durability table compares
in-memory and WAL-backed fsdb with durable and no-fsync MySQL.

The 10x scale run was stopped before completion at the user's request, and the
partial samples are not used here. The sustained load suite was not rerun in
this pass. No claim in this report relies on either suite.

Allocations are measured in the BenchmarkDotNet client process. They mostly
describe MySqlConnector request/result handling, not either server's total
memory use.

## Executive summary

- The median fsdb/MySQL latency ratio is 2.98x. The geometric mean is 2.39x;
  these are descriptive summaries across heterogeneous queries, not an
  application-weighted score.
- fsdb is faster in 23 of 127 paired workloads. Its strongest results are in
  several correlated-query plans, composite membership, full-text/index
  intersections, and a few catalog/grouping paths.
- Point reads have a substantial fixed-cost gap: prepared and ordinary primary
  key reads are 6.80x and 7.21x slower than MySQL. Connection setup itself is
  19% faster, which localizes the gap after authentication and connection
  establishment.
- Full-text performance is broadly competitive. Boolean search, proximity
  search, and point-index intersections beat MySQL; optional-term search and
  natural-language search remain slower.
- The clearest planner cliff is a bounded range written as two inequalities.
  Equivalent `BETWEEN` queries are much faster in fsdb, while MySQL treats the
  spellings similarly. This affects reads, ordered reads, functional indexes,
  and indexed range updates.
- WAL cost is not the main write bottleneck in these tests. WAL adds little to
  the concurrent-insert case and moderate cost elsewhere, yet WAL-backed fsdb
  is still 3.25x to 5.20x slower than durable MySQL.

WAL changes these fsdb workloads by 1.01x to 1.59x. MySQL's durable mode costs
1.91x to 2.47x relative to its no-fsync mode. Despite fsdb paying less extra

publication/index-maintenance and per-command path before lower-level WAL
tuning.

## Index plans versus fsdb scan controls

The benchmark suite includes semantically equivalent expressions that prevent
index matching. This reveals whether fsdb's own optimization pays off even
when MySQL remains faster in absolute terms.

| Indexed path | Speedup over fsdb scan control |
| --- | ---: |
| Indexed disjunction | 23.82x |
| Indexed conjunction | 9.51x |
| Composite-prefix equality | 8.80x |
| Composed functional equality | 125.36x |
| Composed functional range | 8.10x |
| Composed functional range plus unrelated `ORDER BY` | 7.13x |
| Functional-index ordering | 140.52x |
| Correlated functional equality | 1,950x |
| Correlated functional text range | 47.18x |
| Correlated functional numeric range | 396.85x |

The recent range-before-unrelated-order planner change is effective: the
indexed form takes 8.795 ms versus 62.669 ms for the previous scan-shaped
control. The direct functional range also falls from 59.398 ms to 7.329 ms.

Not every index is profitable. The selective secondary count range takes
7.403 ms through the index and 5.576 ms through the forced scan. A half-table
literal `IN` index path is likewise 33% slower than its scan control, while the
broad-list path is only 12% faster. These are cardinality/costing opportunities,
not index-correctness failures.

## Largest actionable gaps

### 1. Merge conjunctive bounds before probing

The equivalent singleton predicates below should have nearly identical plans:

| Predicate shape | fsdb | MySQL |
| --- | ---: | ---: |
| `sort_key >= n AND sort_key < n + 1` | 8.218 ms | 0.084 ms |
| `sort_key BETWEEN n AND n` | 0.388 ms | 0.080 ms |

fsdb is 21.2x faster when the same bound is expressed with `BETWEEN`; MySQL is
essentially unchanged. The two-inequality path likely performs independent
range work and residual processing instead of forming one tight interval.
This also explains the 97.91x ordered-secondary-range gap, the 38.82x
secondary-range-update gap, and much of the 103x to 114x direct functional
range gap.

The best next slice is a normalized bounded-range candidate shared by reads,
ordered reads, functional indexes, and indexed writes. It should intersect
compatible lower and upper bounds before touching index entries and retain the
existing collation-safety checks.

### 2. Reduce fixed per-statement work

Connection setup beats MySQL, but point reads are around seven times slower
and small projections/views are around seven times slower. Profiling should
separate parse, authorization, planning, row lookup, and protocol encoding on
a persistent connection. Prepared statements still take 0.279 ms, so parsing
alone cannot explain the whole gap.

### 3. Simplify replace and write publication

`REPLACE` is 4.58x to 10.39x slower than MySQL. Durability-matched burst tests
show that WAL is not the dominant cost: in-memory fsdb also trails no-fsync
MySQL by 5.05x to 9.79x. The next investigation should measure immutable-page
copying, index reconstruction, conflict/publication retries, and result
encoding separately before changing concurrency semantics.

### 4. Profile the ordinary join and top-orders window

The ordinary inner join is 9.09x slower and the windowed top-orders query is
2.20x slower with a 122 ms absolute latency. fsdb already wins some more
specialized composite and correlated plans, so broad algorithm replacement is
not indicated. Profile these concrete shapes and preserve the existing fast
paths.

## Harness correction made during this run

`bench-durable` previously selected every feature benchmark across four
storage targets, repeating read-only cases whose storage mode cannot affect
the result. It now selects only `Durability`-tagged write workloads. This cuts
the durability phase from 504 mostly redundant measurements to the intended
12 without reducing feature coverage in the standard suite.
