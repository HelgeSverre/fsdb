# Initial FSDB torture baseline — 2026-08-16

Toolchain: FSDB revision `66894b2aca0a7573a3824d18bc2ecb42c831a185`
(dirty working tree), SQL Splitter 1.21.0, MySQL 8.4.11, .NET 10.0.7. All
cases used seed 1, a per-table cap of eight rows, and a ten-second deadline.

| `relational`, batch 1 | 51/51 statements and 3/3 probes | `schema_mismatch`: `memberships` foreign keys absent from FSDB's metadata snapshot | `0f60032dfbd7449482c66663a4262a147aea766b5ac29a950009767e56c2cac8` |
| `commerce`, batch 8 | statement 11 | `fsdb_parser_gap` on a MySQL `X'…'` blob literal in a multi-row product INSERT | `f39eef5e7c13c957e1f3a840b74802ab3652b61bb450e194f44e92e164f1f257` |

MySQL accepted every statement listed above. For both parser findings,
`Fsdb.Parser.parse` rejected the exact statement before FSDB wire execution;
therefore these are parser support gaps rather than executor or protocol
failures.

The relational case accepted all six FK `ALTER TABLE` statements on both
targets. FSDB commit instrumentation reported the schema changes, direct
catalog invariants remained clean after every mutation, and the project-tenant
orphan, nullable task-assignee orphan, and grouped membership-role probes
matched MySQL. The first observable difference was
`information_schema.key_column_usage`: MySQL reported the two membership FKs
while FSDB reported none. This establishes a metadata compatibility gap; the
clean generated data alone does not prove rejection behavior for invalid FK
inserts, so that remains a future negative-oracle scenario.

All three cases were replayed from their artifact manifests and reproduced the
same signatures. No signature was added to `support/known-gaps.json`.

Reproduce the smoke baseline with:

```bash
cd torture
./scripts/run.sh suite
```

## Resolution audit

Resolved later on 2026-08-16. The binary-literal finding was a real engine
gap spanning parser, storage, and wire encoding: FSDB now parses case-insensitive
`X'…'` literals as bytes, retains `VBytes` in binary columns, advertises binary
column metadata, and emits raw bytes without UTF-8 corruption. A subsequent
multi-seed round also exposed a real ENUM ordering gap; direct ENUM `ORDER BY`
keys now use declaration ordinals while explicit character casts remain
lexical. Both fixes have focused tests in the root Expecto suite.

The relational FK finding above was misclassified. FSDB already exposed the
foreign keys; the oracle connection selected its generated database while the
FSDB connection selected none, so `table_schema = DATABASE()` compared against
`NULL` only on FSDB. The harness now selects FSDB's default database and has a
regression test for that connection invariant. Follow-on snapshot differences
were also harness normalization issues: MySqlConnector's boolean representation
and InnoDB's implicit FK indexes are normalized without hiding explicit indexes.

Verification after the fixes:

- all 638 root FSDB tests passed;
- all 22 harness tests passed;
- all three scenarios passed for seed 1 / 8 rows, seed 2 / 8 rows, and seed 17 /
  128 rows: nine differential cases with matching statements, probes, schemas,
  foreign keys, typed row multisets, and catalog invariants.
