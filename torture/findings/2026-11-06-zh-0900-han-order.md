# Chinese 0900 Han collation: ngram parity with ordering divergence

The maintained `ngram-multicol-oracle.py` runs a native MySQL 8.4.11
server beside fsdb. Its two-column corpus under
`utf8mb4_zh_0900_as_cs` produced zero membership or relevance
mismatches across 387 searches at each ngram token size 1–10.

A separate `--legacy-range 4E00:4E40 --weight-checks` run at sizes 1
and 2 found different `WEIGHT_STRING` bytes for all 64 Han characters
at each size. That alone does not establish an SQL ordering difference:
fsdb uses host ICU sort keys, whose bytes need not match MySQL's
representation even when the relative order does.

The added `--order-checks` probe compares `SELECT id FROM docs ORDER BY
body,id` against both servers. All 64 characters in U+4E00–U+4E3F
sort identically. Expanding the indexed document range to
U+4E00–U+4EFF, while searching only U+4E00–U+4E0F, exposes a real
ordering difference. At result position 54, MySQL returns document 127
(乾, U+4E7E); fsdb returns document 130 (亁, U+4E81). MySQL puts 乾
before 亁, 仠, and 仡; fsdb puts it after this run. The 96 full-text
searches in that same run still have zero membership and relevance
differences. A direct `_utf8mb4'乾文' COLLATE utf8mb4_zh_0900_as_cs <
_utf8mb4'亁文' COLLATE utf8mb4_zh_0900_as_cs` comparison returns 1 on
MySQL and 0 on fsdb. The oracle now checks this predicate for the first
order discrepancy as well as the sorted rowset.

The probe also builds `idx_body` on `body(20)` and executes `SELECT id
FROM docs FORCE INDEX (idx_body) WHERE body < '亁文' ORDER BY id`.
MySQL includes document 127 (`乾文`); fsdb omits it. This directly
confirms a row-membership difference in the forced indexed range.

Reproduce with a Release CLI build and native MySQL 8.4.11:

```sh
uv run --with pymysql torture/scripts/ngram-multicol-oracle.py \
  --collation utf8mb4_zh_0900_as_cs \
  --legacy-range 4E00:4F00 --legacy-term-range 4E00:4E10 \
  --order-checks 1
```

## CLDR 30 pinyin source probe

MySQL's Chinese source identifies CLDR 30 tailoring. The independently
published [CLDR release-30 `zh.xml`](https://github.com/unicode-org/cldr/blob/release-30/common/collation/zh.xml)
contains an ordered pinyin sequence. The oracle can compare that sequence
with native MySQL after the file is downloaded locally:

```sh
uv run --with pymysql torture/scripts/ngram-multicol-oracle.py \
  --collation utf8mb4_zh_0900_as_cs \
  --legacy-range 5E00:6E00 --legacy-term-range 5E00:5E10 \
  --order-checks --cldr-pinyin /path/to/cldr-30/zh.xml 1
```

The comparison ranks only characters present in CLDR's long pinyin
sequence and removes unranked characters from both ordered lists:

| Han block | Ranked | CLDR 30 vs MySQL |
| --- | ---: | --- |
| U+4E00–U+51FF | 1,020 / 1,024 | Exact order |
| U+4E00–U+5DFF | 4,087 / 4,096 | 1,138 inversions: `嘸` moves from MySQL position 833 to CLDR position 1,971; the other ranked characters retain their relative order |
| U+5E00–U+6DFF | 4,092 / 4,096 | Exact order |
| U+6E00–U+7DFF | 4,088 / 4,096 | Exact order |

This makes CLDR 30 a promising independent source for a Chinese Han
tailoring implementation. It does not yet prove parity for unranked Han,
mixed scripts, compatibility characters, or `WEIGHT_STRING` bytes, and
the engine still uses host ICU. A production change must preserve one
consistent comparison and index-key order and pass mixed-script and
full-text probes before replacing that path.

## Sort-key encoding constraint

An F# prototype encoded the CLDR rank as private-use Unicode scalars
and passed the transformed string to host ICU. That preserves rank order
between two encoded Han characters, including across a 4,096-rank
boundary. It does not preserve Chinese collation order against other
scripts: host ICU places the private-use marker after `a`, while a
read-only local MySQL 8.0.33 control of the same Chinese collation
reports `WEIGHT_STRING('一')` beginning `A63E` and `WEIGHT_STRING('a')`
beginning `BDC4`, so `一` sorts before `a`. This control is a design
counterexample, not a replacement for the pinned MySQL 8.4.11 oracle.
The private-use encoding was not added to fsdb. A production key needs
the Han order and its placement among non-Han weights, rather than a
single marker followed by a rank.

This is a Chinese collation compatibility gap in sorting, scalar
comparison, and indexed range membership. Correcting only the exposed
character pair would be brittle because MySQL and host ICU have
different tailoring/version data. A complete fix needs a MySQL 8.4
Chinese collation weight source or a broader validated tailoring table.

## Host ICU stroke-order trial

MySQL 8.4.11's [Chinese collation source](https://github.com/mysql/mysql-server/blob/mysql-8.4.11/strings/uca900_zh_data.h)
uses a Chinese-specific CLDR 30 tailoring and build-generated Han weight
pages. The host `zh-Hans-CN-u-co-stroke` ICU variant does put `乾文`
before `亁文`, but it is a different overall ordering. In a temporary
Release build, the U+4E00–U+4EFF oracle's first sorted row changed from
MySQL document 56 to fsdb document 1. Its first scalar comparison and
forced indexed range also disagreed with MySQL, while the 96 ngram
searches still matched. The locale change was reverted and Release
rebuilt from committed code. A simple switch from pinyin to stroke
ordering is not a valid fix.

## Ordering breadth

The oracle now reports displaced sorted positions and pairwise order
inversions when `--order-checks` is enabled. The baseline pinyin-locale
build yields 133 displaced positions and 151 inversions among 256 Han
characters (U+4E00–U+4EFF). Across 1,024 characters
(U+4E00–U+51FF), it yields 457 positions and 1,320 inversions.
Across 4,096 characters (U+4E00–U+5DFF), it yields 3,721 positions
and 41,213 inversions. The 96 full-text searches selected from the
first 16 characters still have zero membership or relevance differences
in the 4,096-document run. The failing first pair changes with corpus
size, and the broad ordering difference cannot be fixed by special
handling only `乾` and `亁`.

```sh
uv run --with pymysql torture/scripts/ngram-multicol-oracle.py \
  --collation utf8mb4_zh_0900_as_cs \
  --legacy-range 4E00:5E00 --legacy-term-range 4E00:4E10 \
  --order-checks 1
```
